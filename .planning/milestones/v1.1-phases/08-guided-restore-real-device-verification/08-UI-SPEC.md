## Screen Contracts

### SCRN-06 — the mobile guided restore flow (`Recovery.tsx`)

**Structural rule (D-01, non-negotiable, identical to phases 6/7):** the desktop stepper JSX
wraps in `max-md:hidden` (always rendered — desktop byte-identical, effects behavior
unchanged); the mobile step flow renders `{!isDesktop && (...)}`. Both halves in the SAME
file, sharing the SAME component state and handlers — the mobile steps fire the identical
`api.ts` calls the desktop stepper fires (D-02). The page root stays `PAGE_SHELL`
(Recovery.tsx:1998); the page `h1` (`recovery.pageTitle`, text-lg) stays on both halves.

Warning signs of a broken gate: duplicate-text locator errors; desktop effects firing under
touch. `desktop-untouched.spec.ts` extends its battery loop to `/recovery`.

**The hue-counter discipline (research Pitfall 1 — contract, not advice).** Recovery's
page-flat `hueSeq`/`nextHue()` counter assigns rainbow positions in JSX evaluation order
(Recovery.tsx:1973-1985). The mobile block either (a) uses its OWN counter, or (b) places
every `nextHue()` call strictly AFTER all desktop calls in render order. A dom test asserts
the desktop-first-N hue sequence survives the mobile block landing. A shifted desktop hue is
a desktop byte-identity regression even when no desktop pixel moved in the hidden half's
layout.

**Step structure (one mobile step per desktop StepCard, desktop order):**

```
┌──────────────────────────────────┐
│ h1  "Disaster recovery"          │  ← page title, unchanged (text-lg)
│ [Step {n} of {total}]   [Back]   │  ← position chip (item 12) + common.back
│ ────────────────────────────────│
│ Step title (existing key)        │  ← the desktop StepCard title, verbatim
│ [status Badge + text label]      │  ← StepState as TEXT, never the bare dot
│                                  │
│ Step body: the desktop card's    │  ← same field components, same handlers,
│ controls re-hosted, scrollable   │    re-hosted in the mobile card language
│ in the page scroller             │    (MobileSectionLabel sections, ≥44px rows)
│                                  │
│ [secondary/tonal rows:           │  ← restore + verify rows live HERE, in the
│  restore-all · per-row restore   │    body — mid-screen, secondary-styled,
│  · verify integrity]             │    NEVER in the thumb-zone bar
├──────────────────────────────────┤
│ StickyActionBar                  │  ← sidebar surface + top hairline
│   primary step action (existing  │  ← Check / Connect & preview / Discover /
│   key) or Continue / Done        │    Continue / Done — the SAFE action owns
│                                  │    the thumb-default position
└──────────────────────────────────┘
```

- **Step gating:** step n+1 is reachable only when step n's prerequisite holds (mirrors the
  desktop disclosure states: readable → config optional → attached → discovered → restored →
  kit). This is 1:1 with the desktop path (D-02) and structurally guarantees the empty-state
  copy contract above (no unreachable-state copy forks).
- **Step state:** the desktop `StepState` ("idle" | "ok" | "warn" | "bad") renders on mobile
  as a Badge with the `statusLabel` TEXT + the status hue — never color alone (VERIFY-05).
- **Back** navigates without resetting completed step state (the shared component state is
  the single source; Back is presentation-only navigation).
- **SCRN-06's five beats** map onto the desktop structure, not beside it: "preflight
  summary" = steps 1-3 (readability, optional settings restore, attach); "confirmation
  naming overwrite consequences" = the restore confirms inside step 4 (ConfirmSheet +
  consequence-naming copy + config.restoreChain narration on the config path); "optional
  dry-run/verify" = the `checkDomain` integrity row in step 4; "live progress with log" =
  `RestoreProgress` + LogList presentation during step 4's restores; "completion" =
  `recovery.restoreAllResult` + the kit step. No new step tree, no new restore types
  (D-02), no new API surface (D-12).

**Restore-all sequencing:** the mobile step consumes the desktop wizard's `restoreAll`
handler verbatim — one restore per target, `fireAndWaitRun` sequential, terminal state
before the next (Recovery.tsx:1923-1961). Never a parallel loop, never a second fire path.
**Settings-write discipline (Pitfall 6):** the connect/config steps route through the
existing `connectPreview`/`restoreOwnConfig` handlers (re-fetch + merge onto the fresh
server baseline before every PUT) — never a direct `putSettings` with a captured object.

**ForeignRestoreCard (research Open Question 1 — recorded default):** stays desktop-only,
rendered INSIDE the `max-md:hidden` wrapper (deliberately absent on mobile) with a
why-comment at the site: it is a separate read-only-session card outside the numbered
wizard path, D-02 scopes the mobile flow to the stepper, and SCRN-06/VERIFY never name it.
Recorded as a known desktop-only surface in the UAT checklist so the device session sees
the decision, not a gap. (The planner may fold it into the flow instead; if so it becomes
a seventh, gated step — the contract's default is explicit absence.)

**RunDetailSheet restore entry (research Open Question 2 — recorded default):** the entry
stays reveal-only (no deep-link into the flow). In the commit where the flow ships, the
stale "the full guided restore is SCRN-06 / Phase 8" note (RunDetailSheet.tsx:64-68,
:561-574) is updated — the comment text AND any user-visible note — to name the shipped
flow. A stale pointer surviving the phase is a documentation bug.
