## Spacing Scale

Declared values (multiples of 4 only — Tailwind's existing scale, no new tokens):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`gap-1`) | icon-to-label gaps inside rows |
| sm | 8px (`gap-2`, `p-2`) | in-card element spacing, chip gaps, chip padding |
| lg | 16px (`p-4`, `gap-4`) | card padding, gaps between cards, sheet internals |
| xl | 24px (`p-6`, `gap-6`) | `main` padding desktop value (`p-4 md:p-6` holds); mobile block column gaps |
| 2xl | 32px | sparse layout gaps |
| 3xl | 40px (`gap-10`) | desktop PAGE_SHELL rhythm (`gap-6 md:gap-10` holds on converted pages) |

**Phase 7 scale decision (the discipline lock).** Phase 6 declared "8/16 stops only" in prose
and still shipped ~24 twelve-pixel values (06-UI-REVIEW, Spacing 2/4). This phase converts the
rule into a failing test: the new-code source-assert guard (model: `mobileShellSource.test.ts`)
grows a spacing sweep asserting ABSENCE of `gap-3|px-3|py-3|pt-3|pb-3|pl-3|pr-3|m[trblxy]?-3|p-3`
and of `gap-1\.5|gap-2\.5|py-2\.5|px-2\.5` in every file this phase's plans touch, and of
`font-medium` in the same files. Guard file lists the phase-7 files explicitly; a legitimate
future exception means editing the guard with a written why, never a silent new value. Existing
pre-phase-7 12px lines are absorbed per the Carried Fixes section, then fall under the guard.

Exceptions (structural dimensions, not spacing tokens):

| Dimension | Value | Why |
|-----------|-------|-----|
| Touch-target floor | ≥44px on every interactive control and list row below the breakpoint | D-11, VERIFY-04; MoreSheet's `min-h-[3.25rem]` (52px) remains the sheet-row precedent |
| FAB | 52px height, `border-radius` from `--mob-fab-radius` (18px under material) | design bible `.fab` (android.html:111-115); its first three visual properties transfer, its `position:absolute` does NOT — placement is in-flow or sticky-in-flow inside the page column with a mandatory why-comment (D-12 sanctions the recorded deviation; Pitfall 4) |
| Sticky bars / editor footers | content row ~56px + top hairline; sticky-in-flow, never `position:fixed` | Phase 6 language, unchanged; `StickyActionBar` keeps its one documented `max(0.75rem, safe-area)` exception |
| Editor sheets | `fullHeight` (`h-dvh`) for D-05 editors; content-sized for D-04 viewers | sheet-type rule: editor = full screen, viewer = content |
| Safe-area insets | `env(safe-area-inset-*)` custom properties only; sheet side padding `max(1rem, var(--safe-area-left/right))` | SHELL-04 contract, unchanged |
| iOS grouped-list cells | cell vertical padding from the 8/16 stops; hairline separators `border-carbon-border` | the maquette's 12px cell padding (`ios.html:69`) maps to `py-2` + row min-height, NOT a new 12px value |

**Platform chrome exception (closed, single-site).** The HIG large title is 32px/700
(`ios.html:62`: `.navbar h1 { font-size: 32px; font-weight: 700; letter-spacing: -0.5px }`).

the platform layer translates it. No page JSX ever writes a 32px or a 700; the 700 exists
nowhere except the custom-property block. Material keeps the existing 20px/600 heading. This
is the phase-6-drift lesson inverted: the exception is narrower than the rule, and it lives in

Monospace register (unchanged): snapshot ids, peer URLs, host paths, log timestamps render
`font-mono` + `tabular-nums` timestamps (ActivityLog pattern). Fleet protection scorecard and
receiver inventory numbers render tabular.

## Platform Chrome Contract (PLAT-01 — new in this phase)

**Mechanism (D-12, research Pattern 2).** `web/src/lib/platform.ts` resolves
`material | cupertino` (closed union), writes it as `data-platform` on `<html>`, and persists
the choice to a `bv-*` localStorage key — the `shape.ts:51-53` + `theme.ts paint()` discipline
verbatim: ONE application function, every read funnels through it, stored values coerced
against the union (never trusted raw). `index.css` gains `[data-platform="material"]` /
`[data-platform="cupertino"]` blocks redefining ONLY custom properties:
`--mob-fab-radius` (18px material), `--mob-title-size`/`--mob-title-weight` (cupertino
32px/700), `--mob-check-radius` (cupertino `999px` — circular checks; material keeps the
existing check radius), `--mob-chip-radius` (`999px` — chips are pills in BOTH languages).
No `navigator.userAgent`/`userAgentData` anywhere (grep-clean slate stays clean; the guard
suite extends a needle for both identifiers in `src/`).

**Decision — platform selection (auto-mode, research A1 adopted):** default `material`,
persisted user override, NO automatic OS detection. A web page cannot honestly distinguish
Android from iOS without UA sniffing, which is banned; `(pointer: coarse)` cannot tell them
apart either. Consequence, stated plainly: until a preference control ships, both platforms
present the material expression; the HIG layer is real and e2e-verifiable via the attribute,
and Phase 8's real-device pass is the scheduled venue to revisit (an explicit Settings control
rides a later polish pass — research Open Question 2). One `usePlatform()` reader is
sanctioned for the genuinely STRUCTURAL switches only: FAB-vs-pinned-button and nothing else.
Everything else (title, checks, chips, radii) is attribute-CSS with zero JSX branching —
Pitfall 5's "no `usePlatform()` conditionals inside page blocks" holds.

| Bible mapping row | Material (`data-platform="material"`) | Cupertino (`data-platform="cupertino"`) | Ship shape |
|---|---|---|---|
| Navigation | navpill bar — BottomNav already ships the pill (Phase 5); unchanged | tab-bar treatment: same component, tint via existing active language | CSS-only; no new nav code |
| Primary action | FAB: 52px, `--mob-fab-radius`, accent fill, `accentContrast` ink; in-flow/sticky-in-flow placement with the recorded why | filled button pinned (the Phase 6 sticky-block language) — the FAB does not render | `Fab` component; structural `usePlatform()` switch sanctioned |
| Header | 20px/600 heading (existing) | large title 32px/700 via `--mob-title-*` | CSS-only |
| Selection check | existing square-ish check | circular via `--mob-check-radius: 999px` — SHAPE ONLY; size/hit geometry from Phase 6 untouched | CSS-only |
| Status badge | tonal chip (existing Badge) | pill badge (existing Badge radius) | CSS-only |
| Lists | cards, `--radius-card` (16px) | inset grouped cells with hairline separators (`border-carbon-border`) | CSS variant on the card stack |
| Toggle | existing switch (unchanged) | existing switch (unchanged) | none — one toggle, no fork |

**Recorded deviation (radius):** the maquette's iOS grouped list uses 14px cell-group radius;
this contract keeps `--radius-card` (16px) — the house rule "never hard-coded radii on
controls" outranks a 2px maquette nicety, and inventing a 14px token for one surface is
exactly the drift the token system exists to prevent.

**FAB surface resolution (auto-mode, research Open Question 1):** the FAB is the primary
trigger on the NEW destination surfaces (VMs backup trigger, Settings' add-style actions where
a surface has one). Home KEEPS its shipped sticky "New backup" block with the recorded-why
comment (Phase 6 SCRN-01 contract stands; it is revisited at Phase 8's real-device pass, not
migrated mid-milestone). Config/Receiver/Fleet primary actions are sheet-opening rows, not
FABs — a FAB that opens an editor sheet duplicates the card row it would sit beside.
